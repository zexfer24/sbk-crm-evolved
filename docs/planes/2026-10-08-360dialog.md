# Plan: SBK CRM pasa de la Cloud API directa a 360dialog

**Fecha:** 8/10/2026 · **Base:** `52a8b4c` (producción, según el diagnóstico del VPS) · **Sin migraciones.**

## Por qué

Se perdió el número de Meta por facturación; el número nuevo (+58 422 894 7095)
vive en 360dialog. El payload del webhook es el mismo de la Cloud API, pero
cambian el host de envío, la autenticación saliente, la descarga de multimedia
y la autenticación del webhook (360dialog no firma con `X-Hub-Signature-256`).
Hoy un evento de 360dialog se rechaza siempre (401 o 503).

## Decisiones (tomadas por el orquestador; objetar antes de aprobar)

- **D1. `WHATSAPP_PROVIDER` sin definir = `meta`.** El código nuevo se puede
  desplegar antes que la variable y se comporta igual que hoy. Un valor que no
  sea `meta` ni `360dialog` es configuración rota: no hay credencial (envíos
  cortan como hoy sin token), el webhook responde 503
  (`whatsapp_proveedor_invalido`) y `/api/health` lo reporta como faltante.
- **D2. Una sola fuente de credenciales:** `src/lib/whatsapp/provider.ts`
  (nuevo, server-only). Ningún archivo de `src/` vuelve a leer
  `WHATSAPP_ACCESS_TOKEN` salvo `provider.ts`.
- **D3. `meta-client.ts` conserva su nombre y sus funciones**; el parámetro
  `accessToken: string` pasa a `credentials: WhatsappCredentials`. Renombrar el
  archivo queda fuera (ruido en 6 importadores, glosario y CLAUDE.md).
- **D4. La API key de 360dialog solo viaja a `D360_BASE_URL`.** La descarga de
  multimedia reescribe `lookaside.fbsbx.com` → `D360_BASE_URL`; cualquier URL
  que, ya reescrita, no tenga el mismo origen que `D360_BASE_URL` se rechaza sin
  hacer la petición (una URL del payload no puede llevarse la llave a otro host).
- **D5. URL de descarga en el webhook:** la doc confirma que existe pero no
  nombra el campo. Se lee `url` del objeto de media (nombre de la Cloud API
  reciente) si viene; si falla la descarga directa, o no viene, se cae al
  camino `GET /{media_id}`. La URL del webhook vale 5 min: la descarga ya corre
  enseguida, después de responder.
- **D6. Token del webhook:** header `x-sbk-webhook-token` contra
  `WHATSAPP_WEBHOOK_TOKEN`, comparando con `timingSafeEqual` sobre el SHA-256 de
  ambos (igual largo siempre, no filtra la longitud). Nunca en la query.
- **D7. Con `360dialog`, una firma de Meta no autentica**, ni el token sirve con
  `meta`: cada proveedor tiene su única puerta.
- **D8. `res.json()` del cliente pasa a `.catch(() => null)`** en los cuatro
  sitios: un 401 de 360dialog por llave inválida puede no ser JSON, y hoy eso
  rompería con un `SyntaxError` en vez de un `MetaApiError` con su `status`.

## Riesgos que el código no puede cerrar (van al reporte del VPS)

1. **Reintentos de 360dialog ante 503.** El 503 de `persistenciaFallida`
   (22/9) depende de que el emisor reintente. Meta lo hace; de 360dialog la doc
   no dice nada. Verificar; si no reintenta, un corte de base vuelve a perder
   mensajes (queda registrado con `webhook_mensaje_no_guardado`).
2. `error.code` de Meta dentro de los errores de 360dialog: verificar con el
   primer fallo real (`metaErrorCode` depende de eso para 131047/131026).
3. `typing_indicator`: si 360dialog no lo acepta, solo queda
   `whatsapp_typing_fallido` como warning.
4. El nombre real del campo de URL en el webhook (D5): mirar el primer payload
   con imagen. Si no es `url`, el camino por `media_id` cubre igual.
